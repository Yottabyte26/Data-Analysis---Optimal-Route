# Q02 机场路径规划问题：完整解题思路与实验流程

## 一、题目背景与核心问题

### 1.1 工程背景

假设需要开发一个机场出行路线推荐系统，为用户推荐从起点机场到终点机场的出行路线。

在实际业务中，不同用户对路线的要求可能不同：

- 有的用户希望中转次数越少越好。
- 有的用户希望整个行程耗时越短越好。
- 有的用户希望总飞行及交通里程越短越好。

这三种优化目标并不相同，因此，即使使用同一张机场交通网络，也可能得到不同的最优路径。

本题的核心任务是：

**基于机场、航空航线和地面接驳数据构建有向加权图，分别使用 BFS 和 Dijkstra 算法求解三种路径优化问题，并比较不同优化口径下的路径差异。**

### 1.2 数据来源

| 数据文件 | 数据规模 | 主要内容 |
|---|---:|---|
| Q02_airports.csv | 620 行 | 机场编号、经纬度、开放状态等 |
| Q02_routes.csv | 7355 行 | 航空航线、航司、耗时、里程、经停及季节信息 |
| Q02_ground_links.csv | 30 行 | 公交、铁路、渡轮等地面接驳 |
| Q02_od_pairs.csv | 200 行 | 200 对起点和终点机场 |

评测日期：2026 年 1 月 15 日。

注意：季节性航线必须按照评测日期判断是否处于运营窗口内。

# 三、第一阶段：数据读取与清洗（必做 A）

## 3.1 数据读取

首先使用 Pandas 读取四个 CSV 文件。

主要检查：

- 数据总行数。
- 字段名称及数据类型。
- 是否存在缺失值。
- 是否存在重复记录。
- 机场 ID 是否唯一。
- 经纬度是否合法。
- 起点和终点机场是否存在。

例如：

```python
import pandas as pd

airports = pd.read_csv("Q02_airports.csv")
routes = pd.read_csv("Q02_routes.csv")

od_pairs = pd.read_csv("Q02_od_pairs.csv")

print(airports.shape)

print(ground.shape)
print(od_pairs.shape)
```

## 3.2 机场数据清洗

机场数据是构建图节点的基础。

主要处理：

1. 检查机场 ID 是否为空。
2. 检查机场 ID 是否重复。
3. 检查经纬度是否缺失。
4. 检查纬度是否在 [-90, 90] 范围内。
5. 检查经度是否在 [-180, 180] 范围内。
6. 排除已关闭机场。

需要注意：

机场数据中存在关闭机场，不能直接将全部 620 个机场作为最终图节点。

最终只保留符合开放状态要求的机场。

## 3.3 航空航线清洗

航空航线是图中的主要边。

需要处理以下问题：

### （1）重复航线

统计完全重复的记录。

对于所有字段完全相同的重复记录，只保留一条。

不能简单地根据起点和终点去重，因为同一机场对可能存在不同航空公司、不同耗时和不同里程的航班。

### （2）共享航班

共享航班通过 codeshare 字段识别。

共享航班不等于完全重复航线。

在缺少实际承运航班对应关系的情况下，不能随意删除所有 codeshare=1 的记录。

本实验保留符合清洗条件的共享航班记录。

### （3）季节性航线

根据评测日期 2026-01-15 判断航线是否运营。

对于全年运营的航线直接保留。

对于季节性航线，根据其运营月份判断是否覆盖 1 月 15 日。

不在运营窗口内的航线不参与建图。

### （4）关闭机场和不存在机场

检查每条航空航线的起点和终点是否都存在于开放机场集合中。

如果起点或终点对应关闭机场，或者机场 ID 不存在，则删除该航线。

### （5）无效里程

航空里程必须是有效的正数。

负里程、缺失里程和无效数值不能作为 Dijkstra 的边权。

## 3.4 地面接驳数据清洗

地面接驳包括：

- bus：公交。
- rail：铁路。
- ferry：渡轮。

地面接驳也应作为图中的交通边，而不能只考虑航空航线。

主要检查：

1. 起点机场是否存在。
2. 终点机场是否存在。
3. 起终点机场是否开放。
4. 交通方式是否合法。
5. 耗时是否有效。
6. 是否存在重复记录。

本实验保留了 30 条地面接驳记录。

地面接驳表没有提供实际交通里程，因此使用机场间 Haversine 大圆距离作为代理里程。

需要明确：该距离不是实际公交、铁路或渡轮线路里程。

# 四、第二阶段：机场交通网络构建

## 4.1 图模型设计

将机场交通网络抽象成有向图：

G = (V, E)

其中：

- V：机场节点集合。
- E：机场之间的交通边集合。

节点表示机场，边表示从一个机场到另一个机场的交通服务。

本实验采用邻接表存储图结构。

示意：

```text
A0001
  |
  +---- flight ----> A0005
  |
  +---- bus -------> A0010

A0005
  |
  +---- flight ----> A0010
```

## 4.2 节点设计

每个机场对应一个节点。

节点 ID 使用机场表中的 airport_id。

例如：

```python
graph = {
    "A0001": [],
    "A0005": [],
    "A0010": []
}
```

最终图包含 612 个开放机场节点。

## 4.3 边的设计

每条交通边保存以下信息：

| 字段 | 含义 |
|---|---|
| dst | 目标机场 |
| mode | 交通方式 |
| airline | 航空公司 |
| duration_min | 交通耗时 |
| distance_km | 交通里程 |
| stops | 边内经停标记 |
| codeshare | 是否为共享航班 |

例如：

```python
{
    "dst": "A0005",
    "mode": "flight",
    "airline": "CA",
    "duration_min": 120,
    "distance_km": 850.5,
    "stops": 0,
    "codeshare": 0
}
```

同一对机场之间可能存在多条不同的交通服务，因此使用邻接表中的边列表保留并行边。

不能简单地把同一机场对合并成一条边。

## 4.4 地面接驳距离计算

航空航线使用原始数据中的 distance_km。

地面接驳没有真实距离字段，因此使用 Haversine 公式计算机场之间的大圆距离。

公式：

a = sin²(Δφ/2) + cos(φ₁)cos(φ₂)sin²(Δλ/2)

d = 2R × arcsin(√a)

其中：

- φ₁、φ₂：起点和终点纬度。
- λ₁、λ₂：起点和终点经度。
- R：地球平均半径，取 6371 km。
- d：两个机场之间的大圆距离。

注意经纬度需要先转换为弧度。

该代理距离仅用于构建最短总里程模型。

目前已构建：

| 指标 | 数量 |
|---|---:|
| 节点 | 612 |
| 航空边 | 5191 |
| 地面边 | 30 |
| 总边数 | 5221 |

最终得到一张包含航空和地面交通方式的有向加权多重图。

# 五、第三阶段：三种路径规划算法（必做 B）

这是整道题的核心。

三种算法使用同一张图，但优化目标不同。

## 5.1 BFS：最少交通段数

### 优化目标

寻找从起点到终点经过交通边数量最少的路径。

数学表达：

min |P|

其中 |P| 表示路径包含的交通边数量。

### 为什么使用 BFS？

BFS 使用先进先出队列，按照距离起点的边数逐层搜索。

搜索过程：

1. 将起点加入队列。
2. 访问当前节点的所有邻接边。
3. 将尚未访问的目标节点加入队列。
4. 逐层向外扩展。
5. 第一次到达终点时，得到最少边数路径。

例如：

```text
A0001 → A0005 → A0010

A0001 → A0008 → A0009 → A0010
```

第一条路径包含 2 段，第二条路径包含 3 段。

BFS 会选择第一条路径。

### 换乘次数

本实验采用：

换乘次数 = max(0, 交通段数 - 1)

例如：

| 交通段数 | 换乘次数 |
|---:|---:|
| 1 | 0 |
| 2 | 1 |
| 3 | 2 |
| 4 | 3 |

注意：这里的换乘次数是按图边衔接计算的，不代表真实航班换乘次数。

## 5.2 Dijkstra：最短总耗时

### 优化目标

寻找整个行程累计耗时最少的路径。

数学表达：

min Σ duration(e)

其中 duration(e) 是每条交通边的耗时。

### 为什么使用 Dijkstra？

因为每条边的耗时是非负权重，可以使用 Dijkstra 求解单源最短路径。

核心过程：

1. 起点距离设置为 0。
2. 其他节点距离设置为无穷大。
3. 使用优先队列选出当前距离最小的节点。
4. 遍历该节点的所有邻接边。
5. 如果经过当前节点能够缩短到达邻居的耗时，则更新距离。
6. 记录前驱节点和前驱边。
7. 直到终点确定最短距离。

松弛公式：

dist(v) = min(dist(v), dist(u) + w(u,v))

其中 w(u,v) 是交通边耗时。

注意：本实验使用边上提供的耗时，不包含额外的候机、换乘等待、安检和延误时间。

## 5.3 Dijkstra：最短总里程

### 优化目标

寻找累计交通里程最短的路径。

数学表达：

min Σ distance(e)

其中 distance(e) 为交通边的里程。

算法流程与最短耗时完全相同。

唯一变化是边权：

- 最短耗时：duration_min。
- 最短里程：distance_km。

因此，不需要重新设计一套 Dijkstra，只需要改变权重字段。

需要说明：本实验的总里程由航空原始里程与地面 Haversine 大圆代理里程组成，并非所有交通方式的真实运营里程。

## 5.4 三种算法的核心区别

| 算法 | 优化目标 | 核心方法 |
|---|---|---|
| BFS | 最少交通段数 | 按层搜索 |
| Dijkstra | 最短总耗时 | 按耗时权重搜索 |
| Dijkstra | 最短总里程 | 按里程权重搜索 |

# 八、第六阶段：口径冲突分析（必做 C）

## 8.1 什么是口径冲突？

题目要求找出：

按最少中转选择的路线，其总耗时超过最短耗时路线两倍的 OD。

判定条件：

BFS 总耗时 > 2 × Dijkstra 最短总耗时

例如：

某对 OD：

- BFS 耗时：2750 分钟。
- Dijkstra 最短耗时：461 分钟。

耗时比：

2750 / 461 ≈ 5.97

说明 BFS 路线的耗时接近最短耗时路线的 6 倍。

## 8.2 当前实验结果

200 对 OD 中：

- 满足冲突条件：49 对。
- 冲突比例：24.50%。

平均耗时：

| 算法 | 平均耗时 |
|---|---:|
| BFS | 2265.97 分钟 |
| Dijkstra | 1427.435 分钟 |

耗时比最高的三个案例：

| OD | 起点 → 终点 | BFS 耗时 | 最短耗时 | 耗时比 |
|---|---|---:|---:|---:|
| 29 | A0412 → A0463 | 2750 | 461 | 5.9653 |
| 167 | A0304 → A0560 | 2896 | 536 | 5.4030 |
| 135 | A0053 → A0533 | 1169 | 254 | 4.6024 |

## 8.3 冲突产生的原因

最重要的是理解：

BFS 只考虑交通段数，不考虑每条边的耗时。

因此，它可能选择一条交通段较少、但单段耗时非常长的路线。

例如：

```text
路线 A：
3 段，总耗时 2750 分钟

路线 B：
3 段，总耗时 461 分钟
```

虽然两条路线段数相同，但耗时差距非常大。

另外，地面接驳数据中 stops 字段均为 0。

需要注意：审查确认，地面接驳的 stops 字段全部为 0，而航空边的 stops 是边内经停标记。二者不能混淆，也不能直接把 stops 当成 BFS 的换乘权重。

本项目目前没有证据证明 stops=0 就代表真实交通中不需要换乘。

## 8.4 向业务方推荐哪种算法？

如果业务目标是给普通出行用户推荐路线，我会优先推荐：

**Dijkstra 最短总耗时。**

原因：

1. 更符合用户希望尽快到达目的地的需求。
2. 可以综合考虑航空、公交、铁路和渡轮的耗时。
3. 相比 BFS，可以避免单纯追求少换乘而产生明显绕行或耗时过长的问题。

代价：

- 可能经过更多交通段。
- 可能需要更多次换乘。
- 不一定具有最短总里程。
- 当前耗时不包含候机、等待和延误等真实运营因素。

如果用户特别在意少换乘，可以提供 BFS 作为另一种选择。

# 九、第七阶段：差距分布图

使用 200 对 OD 的 BFS 和最短耗时结果，计算两个指标：

### 1. 节省时间

节省时间 = BFS 总耗时 - Dijkstra 最短耗时

### 2. 耗时比

耗时比 = BFS 总耗时 / Dijkstra 最短耗时

绘制两个直方图：

- 左图：200 对 OD 的节省时间分布。
- 右图：200 对 OD 的耗时比值分布。

# 十、进阶任务 D：规模与预处理

题目提出，当 OD 查询量从 200 增长到 20000 时，是否值得预计算全源最短路或连通分量。

### 10.1 可能的方案

方案一：每次查询独立运行 Dijkstra。

方案二：预计算全源最短路径。

方案三：预计算连通分量或弱连通分量。

### 10.2 需要比较的指标

| 指标 | 含义 |
|---|---|
| 预处理时间 | 初始化或预计算所花费的时间 |
| 单次查询时间 | 查询一对 OD 所需的时间 |
| 内存占用 | 预处理结果需要的存储空间 |

### 10.3 分析思路

当前图只有 612 个节点，规模较小。

如果只查询 200 对 OD，逐次运行 Dijkstra 通常足够。

如果未来有大量重复 OD 查询，可以考虑缓存常用起点的最短路结果，或者根据实际需求采用全源最短路预计算。

连通分量适合用于提前判断某些节点之间是否可能连通，但本题是有向图，不能直接把无向连通分量当成有向可达性。

建议通过实际计时和内存测量进行比较，不预先假定全源预计算一定更快。

## 十五、最终总结

这道题最重要的不是简单地实现三个算法，而是理解三个算法的优化目标为什么不同。

- BFS 解决的是最少交通段数问题。
- Dijkstra（耗时权重）解决的是最短总耗时问题。
- Dijkstra（里程权重）解决的是最短总里程问题。

同一张机场交通网络，因为边权定义不同，最终得到的路径也可能不同。

本实验通过 200 对 OD 的批量计算，发现三种算法的路径存在明显差异，其中 49 对 OD 的 BFS 路线耗时超过最短耗时路线的两倍，占全部 OD 的 24.50%。

因此，在实际机场出行推荐系统中，不能只根据交通段数决定最优路线，而应该首先明确业务目标，再选择对应的路径规划算法。

**核心思想：先明确优化目标，再构建权重模型，最后选择合适的图算法。**
